## 任务目标

3. 每个模块产出标准 API 参考：来源归属、加载方式、函数清单（签名或实参形态）、字段/子表、类结构，全部带置信级标注；
4. 全部 82 个无源码模块必须以 dump 值证据为主要依据，辅以调用点反查与语义推测；
5. **服务端能力实测**：对重点模块（`backend`、`room`、`tds_score`、云变量相关）不止于静态研究——拉起真实调试环境做**实机验证**（见「服务端能力实测研究」章节），实测结论回写 API 文档（标注【实测】）。

**范围说明**：`@p_55a3/*`（bgd_game_server / bgd_libs_server / obj / scene / main / trigger_*，共 147 键）是游戏项目自身代码，**不属于本任务**——本任务只研究引擎/官方库分发的模块。draft_v1 中的 `project-bgd.md`、`project-obj.md` 保留存档但不参与迭代。

## dump 结构（已查明，直接采信）

- 全文件是**一个** package.loaded 序列化对象；363 个 `@` 键各出现恰好一次（其中 216 个非 `@p_55a3`），按哈希序散布全文；引号以 `\"` 转义形态存在。
- 值被深度序列化：`"<function>"` = 函数、`"<cyclic reference>"` = 循环引用、`"<max depth exceeded>"` = 超深截断。值形态统计：`true`×172、`{}`×31、完整对象×157、`"<function>"`×3。
- **值展开会把共享引用内联**：例：`@common/base/position` 的值从 14.55MB 展开到 15.93MB（约 1.4MB），内联带出了 base.game 子模块（`backend`/`room`/`select_hero`/`unit_map`）、TriggerEvent 派生类（`EventRegionLeave`/`EventPlayerCheat`）、lua_plus 扁平函数等。解析值树时必须处理这种"一个值里装下半个全局空间"的情况。
- `backend` 实锤字段（样本）：`parse_detail / query_score_log_by_user / stay / query_admin_email / query_score_log_detail / query_score_log / init_game_config / set_log_sample_per_sessions / query_user_payment / send_email / url / query_user_email`（后端日志/埋点查询模块）。
- **归属陷阱（已实测）**：`backend`/`room` 在 dump 全文只出现 1 次，且唯一出现处在 `@common/base/position` 的值内联展开里（`select_hero`/`unit_map` 同区域重复出现 10+ 次）。`backend` 无顶层键，语义宿主是 `base.game.backend`。**做"字段归属修正"剔除内联共享表时，这类"唯一出现处"的字段必须保留并归到语义宿主**，否则会漏。剔除 `@p_55a3/*` 不影响这些字段的覆盖（宿主键 `@common/base/position` 在范围内）。

## 核心新增工作（相对 draft_v1 的增量）

1. **写值树解析器**：对 dump 做健壮解析（转义引号、嵌套表、三种标记、GBK 乱码容忍），按 216 个顶层键切分，提取每键的字段树：函数名、子表路径（如 `backend.url`）、类结构（`____super`/`prototype` = TypeScriptToLua 类）、数据表键样本。截断处（`<max depth exceeded>`）必须标注"此处被截断，字段不全"。
2. **字段归属修正**：值内联展开会混入被引用的其他模块内容——解析时需识别字段归属（属于本模块 vs 被内联的共享表），不能照搬。可用"同一子表在多键值中重复出现"来识别共享表。
3. **升级 82 个无源码模块**：以值树字段清单为主证据替换/补充 draft_v1 的"调用点反查"（值树是直接实锤，反查是间接推测）。
4. **核验 134 个有源码模块**：源码提取的签名 vs dump 运行时字段做对照，标注"运行时存在但源码未见"（动态注册）与"源码有但 dump 未见（未加载/被截断）"的差异。

## 服务端能力实测研究（与文档化并行）

1. **云变量服务端直读直写（重点，此前完全空白）**：客户端 Entrance 协议直读已走通（cloudvar-01~10 + entrance_client），服务端从未研究。要回答：服务端 `base.s.*`/`score.*`/`tds_score.*` 底层走什么通道（与客户端 Entrance 是否同一服务/协议）、签名与读写计次规则、能否像客户端一样绕过封装直连直写、服务端权限面差异。手段：源码溯源（lua_plus 的 tds_score/score 包装器）→ 抓包（entrance_sniff/frida_capture 思路用于服务端进程）→ 协议对照 cloudvar-04-protocol.md → PoC 实测。
2. **backend 模块实测**：`base.backend.url` 已被用户验证可用（url_demo.lua）。实测边界：HTTP 方法/headers/body（GET 以外是否支持 POST）、超时、返回结构、是否计次/限频；`query_score_log*`/`query_user_payment`/`send_email`/`stay`/`init_game_config` 等 query/admin 系列的语义与所需前置（如 init_game_config 是否必须先调）。
3. **room 模块实测**：`find_game_list`/`find_room`/`sync_room_info` 的语义（房间列表查询？跨房匹配？）与返回结构。
4. **协程模型**：服务端哪些 API 必须在协程内调用（url 类、查询类），`base.wait` 与 `co.async` 的正确范式——以 url_demo.lua 为起点归纳通用规则。

实测环境：编辑器 PIE 调试 或 mini-runtime 脱机运行时 B 模式（api-13 编辑器运行时）；测试项目 test_res002。
